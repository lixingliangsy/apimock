Mock servers vs OpenAPI examples

OpenAPI examples are sample payloads embedded in a specification: static, precise, and ideal for documentation. A mock responds to requests, which is what you need once the frontend is actually calling something. The choice is not which is better — it is which stage you are at.

Key takeaways

  • Examples are for reading; mocks are for calling. Documentation and integration need different things.
  • Examples drift silently because nothing exercises them; mocks drift loudly, because a request fails.
  • Generating a mock from a description is fastest when the endpoint does not exist yet.

Where each one wins

  • Examples. Documentation, review, and SDK generation. Precise payloads with no moving parts.
  • Mocks. Frontend integration, demos, and testing states that are hard to reproduce against a real backend.

How to choose

  1. If the consumer is a person reading docs, write examples.
  2. If the consumer is code making requests, generate a mock.
  3. If the endpoint does not exist yet, describe it and mock it — that is the fastest path to a working frontend.
  4. Once the backend exists, keep the contract and validate real traffic against it.

Frequently asked questions

Do we need both?

Usually. Examples for the docs, a mock for the integration work. They can come from the same specification.

Can examples replace a mock?

Not once code is making requests — an example cannot answer one.

Does MockDeck run the mock server?

No. It generates the specification and sample responses; serving them is a separate step.

How do we stop the mock drifting from the real API?

Validate real traffic against the contract in CI. A mock that nobody checks becomes fiction.

Are the sample responses production data?

No. They are generated to look realistic and should be treated as test data.

Which format should we start with?

OpenAPI 3 if you want tooling support; Postman if your team already works there; raw routes if you only need something to call.
