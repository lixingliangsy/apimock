Contract-first API mocks

Contract-first mocking means agreeing the shape of an endpoint — path, method, request fields, response fields, error cases — and generating a mock from that description before the implementation exists. The contract is the artefact; the mock is a byproduct you can build against.

Key takeaways

  • Write the error responses into the contract too; a frontend that has only ever seen 200s breaks in production.
  • MockDeck generates a mock API spec from a description — it is not a live gateway and does not run your backend.
  • Sample data should look real: realistic values surface formatting and empty-state bugs much earlier.

What a contract-first mock needs

  • Path, method and the auth expectation.
  • Request body and query fields, with which are required.
  • Success response: status, headers, and the full field list with types.
  • Error responses: validation failure, not found, unauthorised, rate limited.
  • Realistic sample values, including empty and long values.

How MockDeck fits

Describe an endpoint and MockDeck returns a mock API spec — OpenAPI 3, Postman, or raw routes — with realistic sample responses, so the frontend team can build against something that behaves like the real API while the backend is still being written.

Where it stops

It generates a mock specification, not a running service. Serving the mock, validating real traffic against the contract, and enforcing the contract in CI are separate steps with their own tooling.

Frequently asked questions

Is this a running mock server?

No. MockDeck generates the mock API specification — OpenAPI 3, Postman or raw routes. Serving it is a separate step.

Can it call our real backend?

No. It does not proxy or run your backend; the output is a specification and sample responses.

Which formats does it produce?

OpenAPI 3, Postman collections, or raw routes.

Why bother with error responses in a mock?

Because that is where frontend code usually breaks. A mock that only returns 200s hides the states you most need to handle.

How realistic is the sample data?

It is generated to look like real payloads, which is enough to catch formatting and empty-state bugs early. It is not production data.

Does it validate our existing API against the contract?

No. Contract testing and validation are separate tooling.
